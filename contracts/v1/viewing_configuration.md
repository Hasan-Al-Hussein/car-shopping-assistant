## Exact stored envelope and bounded types

`rules_json` is one object with exactly these seven required keys, no extras or inferred defaults:

| Key | Exact material / validation |
| --- | --- |
| `format` | Literal `viewing-configuration-1` |
| `calendar_version` | Exact `ViewingRules.version`, currently `DEMO-POLICY-1:viewing-calendar-1`; this is the calendar implementation/policy version, not the whole configuration ID |
| `policy` | Complete JSON form of the existing strict `DemoPolicy`, including every explicit default field; revalidate against the injected `ViewingRules.policy` |
| `venue_label` | Exact current `VIEWING_VENUE` / frozen wire literal, including its final full stop |
| `eligibility` | Exact JSON form `{version, eligible_refs}` of existing `EligibilityPolicy`; `version` is its ASCII 1–64-character label; `eligible_refs` is a sorted, unique array of 0–100 complete immutable `{namespace,snapshot_id,source_id}` references |
| `inventory` | Exact complete existing `InventoryObservation.model_dump(mode="json")`: generation, positive active_revision, non-null snapshot_id/index_version/mode |
| `mapping_digest` | Lowercase 64-hex complete `lineage_version` of the accepted active snapshot's reviewed mappings, as retained in the audited stage payload |

The envelope's canonical UTF-8 JSON is at most **65,536 bytes**. This is a proposed configuration input/read bound, not a change to global request or Inventory bounds. Validate stored JSON byte length before materializing a corrupted overlarge row. Reject missing/extra fields, unknown formats, malformed values, duplicate refs, unsupported policies and any normalization/default filling that changes the persisted material. Require every configured ref to have the bound active snapshot ID and its actual snapshot namespace. Sort refs lexicographically by `(namespace, snapshot_id, source_id)` at trusted authoring; require this canonical order on read. Do not silently reorder malformed stored material.

Validate persisted material through the strict model's **JSON mode** (`model_validate_json` on the bounded canonical JSON), then compare canonical UTF-8 JSON bytes for the complete JSON-mode round trip and original material. Ordinary Python dictionary equality is insufficient because it can equate booleans, integers and floats. In particular, strict `DemoPolicy.open_weekdays` is a tuple internally and an array in JSON; Python-mode validation of the stored array is not the persistence contract. Round-trip equality must still reject missing defaulted fields or coercion; JSON mode does not authorize filling omissions.

The bounded loader must select **raw text**, not call `db.get(RuleVersion, ...)` and then measure an already decoded SQLAlchemy JSON value. In the same transaction, a fixed parameterized query can select the version columns, `typeof(rules_json)`, `length(CAST(rules_json AS BLOB))`, and `CASE WHEN typeof(rules_json) = 'text' AND length(CAST(rules_json AS BLOB)) BETWEEN 1 AND 65536 THEN CAST(rules_json AS TEXT) ELSE NULL END`. Reject a non-text/overlarge/null result before JSON parsing; then validate, enforce the canonical byte bound and require the complete round trip. This caps application materialization/validation, not database I/O against arbitrarily corrupted storage. SQLAlchemy text/scalar projections must avoid the column's automatic JSON result decoder.

An explicit empty array is a valid configured deny-all list. Missing `ActiveRules`/configuration is unconfigured. A valid nonmember is ineligible. Missing/stale/invalid reviewed mappings or corrupt dependencies are unavailable; do not map them to ordinary ineligibility. All allowed members require explicitly reviewed resource mappings at configuration adoption. Eligibility membership and physical/simulated vehicle identity remain separate concepts.

Ownership: Transactions should define the small strict internal envelope validator in its new viewing configuration/admission source after adoption. Reuse existing policy/ref/observation validators and error vocabulary; no public DTO or generic configuration framework. Platform owns storage/schema contract. The trusted operator later authors/adopts immutable configuration material; buyers/models never submit or activate this envelope. Brain reviews exact real allowlist/mappings/hash before any real activation.

## Derived identities and wire meaning

1. **Whole configuration ID:** let `C` be canonical serialization of the fully validated seven-key envelope using `json.dumps(..., sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False).encode("utf-8")`. Set `RuleVersion.version = "viewing-config-1:" + sha256(C).hexdigest()`. The format is part of `C`; no ID is embedded back into its own preimage. This 81-character ID fits existing `ShortText` and T6 bounds. `created_at` and the activation revision are not in this content hash.
2. **Policy column:** `RuleVersion.policy_version == envelope.policy.version`. This is the existing F04 policy version, not the allowlist's label.
3. **Effective eligibility version:** preserve BE13's exact existing preimage and serialization: `{algorithm: "viewing-eligibility-1", policy_version: envelope.eligibility.version, eligible_refs: sorted complete refs, inventory: envelope.inventory, mapping_digest: envelope.mapping_digest}`; digest `json.dumps(material, sort_keys=True, separators=(",", ":")).encode("utf-8")`. Set `RuleVersion.eligibility_version = "viewing-eligibility-1:" + allowlist_label + ":" + digest`. Do not substitute the whole-config hash, policy label or mapping_version. The maximum label length still fits 200-character wire/T6 fields.
4. **Active pointer:** `ActiveRules.version` refers to that immutable row; `ActiveRules.revision` / `PreparedViewing.configuration_revision` use existing strict `Revision` bounds, 0 through 2,147,483,647, and a monotonic activation revision checked separately. Reject exhaustion without wrapping or resetting. Repointing or explicitly reactivating after another configuration increments it. Reading or replaying never changes it. Creating a row does not activate it.
5. **Wire review:** `BookingReview.rules_version`, relational review rules_version and `PreparedViewing.configuration_version` carry the whole configuration ID. `ViewingRules.version`, calendar validation's `expected_rules_version` and internal `ZonedInterval.rules_version` continue to carry the calendar version. The later wire options adapter emits the whole active configuration ID. Never pass a whole-config ID into `ViewingRules.validate_interval(expected_rules_version=...)` or silently change the BE13 calendar API.

Changing any calendar/policy/venue/allowlist/inventory observation/mapping material creates a new configuration ID. Changing inventory activation revision, generation, index/mode, snapshot or mapping digest also changes the effective eligibility version. Refresh/reimport/restore never carries permission forward automatically, including reactivation of identical bytes under a new inventory revision. An old configuration may remain retained for historical review/outcome integrity but cannot admit a new action against a different current binding. This is conservative invalidation, not automatic new consent.

## Coherent prepare with the current I5 interface

No new I5 callable or schema column is required by this proposal. `DraftInventory.prepare(ref)` remains outside a write transaction:

1. Obtain one exact selected-ref batch via `CompactInventoryReader.read_refs((exact_ref,), expected_snapshot_id=exact_ref.snapshot_id)`. Require one matching current listing item and preserve `CompactBatch.identity` without parsing/replacing it. Retain the optional mapping/resource observation, but do not require a mapping before checking explicit permission: a configured nonmember, including an empty allowlist, is ineligible even when it has no mapping. Inventory integrity failures still propagate; a corrupt mapping is not treated as ordinary absence.
2. Open one following authorized/trusted **Store READ unit**. Inside it, call I5 `recheck_identity(existing_session, batch.identity, expected_refs=(exact_ref,))` first, then read `ActiveRules`, its one bounded `RuleVersion`, and the required current inventory/profile scalars. Compare the complete bound observation to the freshly rechecked batch. This final unit makes configuration and the already prepared Inventory observation coherent; two unrelated reads without this recheck are insufficient.
3. In that same READ unit, project only the stage payload's top-level `mapping_digest` using a fixed SQL JSON path, and validate its type/64-hex shape and supported serialization version. Compare it to the envelope. Do not load/decode/re-extract the whole candidate/stage in application code. The scalar alone is not trusted evidence: I5's same-unit authenticated complete fingerprint and cold audit establish the stage/mapping consistency behind it. SQL JSON projection cost remains a runtime measurement gate.
4. Validate the strict envelope, content-derived row ID, policy and effective eligibility columns. First require explicit exact-ref membership; a valid nonmember is ineligible. Only for a member require the selected item's reviewed mapping/resource and their exact agreement. This preserves BE13's membership-before-mapping semantics. Bind the active config ID/revision into `PreparedViewing` and preserve the exact I5 identity. Fail closed on absent admission, changed pointer, generation or content. Do not return an unverified token or fabricate a missing result on an integrity exception.

The second read rechecks the original compact token against its own transaction snapshot; it does not call another Store operation from within a Store unit. Its retained token binds the entire accepted snapshot, stage metadata, mappings, resource versions and dependencies. The configuration ID/revision bind the independently validated finite permission envelope. No owner or action authority is cached in either identity.

## Same-unit use and confirmation

Inside the caller's existing `OwnerUnit`, retain fresh credential/owner/session/revision/expiry/action checks and the actual write boundary for effects. Do not start a nested Store unit or call a provider/file/Inventory full-stage decoder.

- Recheck generation and current active inventory observation; exact listing, mapping resource ID/mapping_version and resource existence must match `PreparedViewing`. Resource-version/content changes are also covered by the I5 identity; do not conflate the mapping row's version with `VehicleResource.mapping_version`.
- Call `I5.recheck_identity` with the exact prepared singleton ref inside this same transaction. Its token is opaque and process-bound. Admission revocation, process recreation or content changes fail closed; caller-supplied or stored strings never become a replacement capability.
- Read the bounded current `ActiveRules`/`RuleVersion`; require both ID and activation revision to match preparation. Validate the finite envelope, recompute its whole-config ID and effective eligibility column, compare calendar/policy/venue and inventory observation, and explicitly check exact-ref membership again. A two-key rules_json equality or a version-column-only check is insufficient.
- No second large stage JSON projection is required in the write: the prepared read established the envelope's mapping_digest against the audited stage, the unchanged content-derived configuration ID retains that material, and the I5 token's fresh same-unit fingerprint proves the same stage/mapping/resource content. If preparation did not establish that binding, reject rather than assume it. Parsing/hashing the bounded configuration is permitted; reconstructing the full Inventory is not.
- Existing immutable terminal replay/reconciliation remains authoritative and must not require current eligibility to recreate a past success/rejection. A pending/unknown operation is not made fresh by configuration invalidation. New draft/review creation or a fresh confirmation must satisfy the appropriate current binding and explicit consent rules.

If T6 retains the opaque `PreparedViewing.identity` in an immutable review, deserializing it does not mint authority. A process restart/recreated reader can invalidate that token: GET must fail closed or project an explicitly non-actionable current status under the accepted DTO, and submit must not act on it. Only explicit refresh of never-submitted intent may obtain fresh Inventory/configuration admission and issue a new bound review while retaining the old review/key history. Submitted/unknown intent stays under original-operation reconciliation; known terminal lookup bypasses current admission. This is a production composition constraint, not evidence that OS restart is already implemented or tested.

The active configuration is immutable material, not a cryptographic proof of operator permission: only trusted future configuration tooling may create/repoint it after review. Direct arbitrary database mutation is outside buyer input authority, but in-place payload tampering without a matching content ID must still fail closed. Retain referenced historical rules instead of rewriting them.
