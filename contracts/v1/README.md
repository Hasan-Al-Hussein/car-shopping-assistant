# API and domain contract v1 — freeze candidate

Status: **PREPARED, NOT FROZEN**. Brain accepts F-01 first, then inspects F-02's actual generated artifacts and validation evidence. No application behavior is proven by this document. Canonical output: `${PROJECT_ROOT}`.

## One source of wire truth

Pydantic definitions live in `backend/app/api/schemas/`. `routes.py` specifies exact methods, paths, request/response models, operation IDs, private/mutation flags and domain ownership. `contracts/export_openapi.py` produces `contracts/v1/openapi.json` without opening a store or invoking a provider. `npm run generate:api` in frontend produces only `contracts/generated/api.ts`. Frontend must import these types; internal view models may transform them but must not invent another API definition.

The schema-only application is never mounted by `app.main`. Its deliberately nonfunctional handlers exist solely to generate OpenAPI. Domain implementers expose `router` in `app/<domain>/router.py`; Platform wires real routers in `app/main.py`. Actual routes must use the canonical request/response schemas and operation IDs. BE-25 diffs actual OpenAPI against this frozen surface; contract availability does not imply runtime readiness.

## Endpoint and screen responsibility

All suffixes below are under `/api/v1`. The scoped reference path is `/{namespace}/{snapshot_id}/{source_id}`. Each segment is validated; original source ID remains a string. No bare numeric-ID fallback or implicit newest-snapshot resolution exists.

| Method / path | Owner / purpose | State effect |
| --- | --- | --- |
| GET health, GET config | Platform; all surfaces' capability notices | Read-only; separate store/inventory/viewing/export/assistant states |
| POST identity/bootstrap | Platform; explicit local-continuity notice | Establish only a new empty owner or return existing valid credential context |
| GET identity, POST identity/end | Platform; continuity/revocation | GET never rotates/touches state; end revokes credential without deleting records |
| POST sessions, GET sessions/{session_id} | Platform; new conversation/current state | New chat retains owner and single active Journey; GET read-only |
| GET sessions/{session_id}/messages | Platform; retained historical turns | Bounded cursor read; original user text and typed result; no resubmission/provider call |
| POST sessions/{session_id}/presentations | Platform; explicit owned result interaction | Register server-signed immutable presentation after revision check |
| PATCH sessions/{session_id}/selection | Platform; buyer-selected exact car | Explicit revision-bound selected reference; no booking/lead |
| POST sessions/{session_id}/messages | Assistant adapter with Platform turn persistence | Payload-bound message ID; authorized services only |
| POST inventory/search | Inventory; public explore/refine/paginate | Read-only even with a cookie; never persists session/presentation |
| GET listings + scoped reference path | Inventory; direct/public detail and historical state | Read-only exact reference |
| POST comparisons | Inventory; 2–3 distinct refs | Read-only; each missing/historical result remains independent |
| GET preferences, PATCH preferences | Platform; core explicit recall/remember/correction | Revision-bound durable scope only; one-time criteria are separate |
| GET shortlist, PUT/DELETE shortlist + scoped path | Platform; owned save/remove | Desired-state command with retry ID and aggregate revision; no lead/booking |
| POST viewing-options | Transactions; bounded simulated slot observations | Read-only, time-stamped, no hold; never rewrites rejected operation |
| POST booking-drafts, GET/PATCH booking-drafts/{draft_id} | Transactions; select/time/review/suspend/discard | POST/PATCH explicit; GET cannot create/renew a review |
| POST booking-drafts/{draft_id}/confirm | Transactions; exact simulated confirmation | Only shared authoritative short transaction may commit |
| GET operations/{operation_key}, GET bookings/{booking_id} | Transactions; owned recovery/receipt | Read-only; absence is not noncommit proof |
| POST leads, GET leads/current, GET/PATCH leads/{lead_id} | Transactions; explicit local enquiry/correction | Create-only POST with replay dedupe; corrections need revision; one lead per owner/Journey; no dealer delivery |

No operator, bulk CSV, cancellation/rescheduling, universal deletion, feedback or optional-feature endpoints are included. Screen paths remain Frontend-owned; this table describes capabilities, not a new navigation proposal.

## Identity and transport

- Resolve owner solely from a verified host-only HttpOnly opaque cookie (`csa_owner` for loopback HTTP; the separately configured secure profile may use `__Host-csa_owner`). Credential contains at least 256 random bits; only its digest is stored. Fixed 30-day lifetime; no write/renewal on GET.
- Bootstrap requires explicit notice version/acknowledgement, JSON and exact Origin/Host. A valid cookie returns its current context, without rotation or name matching. Lost response is reconciled with GET identity before another bootstrap. Missing cookie returns anonymous; supplied expired/revoked/unrecognized credentials return uniform 401. Never automatically bootstrap after a private 401.
- Every private route checks cookie ownership; private requests carry `X-Identity-Context` matching that credential's public context ID. This is an equality guard, never independent authority. Private mutations also require credential-bound `X-CSRF-Token`, exact Origin and JSON content type, except bodyless DELETE uses its specified headers.
- DELETE shortlist carries `X-Client-Action-ID` and `X-Expected-Revision`; PUT uses the equivalent bounded JSON fields. The normalized command fingerprint includes method, exact ref and expected revision.
- Private responses and denials are `Cache-Control: no-store`. The frontend keys memory-only caches by context plus local epoch, clears them on identity change, discards old-epoch/context replies, notifies other tabs only of invalidation, and revalidates before showing BFCache-restored private state.
- Uniform 404 covers authorized absent and other-owner private objects. Neither guessed refs nor keys grant access. Origin/Host configuration is exact loopback-only by default; no wildcard credentialed CORS. GET/prefetch/status never writes domain state.
- Response metadata carries request ID, contract/policy version, relevant source/store/entity version and private identity context. Request IDs identify transport attempts, not logical commands.

## Facts and search

`InventoryRef = {namespace,snapshot_id,source_id}` is immutable. Snapshot IDs are 64-character lower-case SHA-256 identities that include source/import policy identity; source IDs are retained strings. Resource identity for capacity is a separate UUID and is never inferred from similar labels or image URLs.

Known facts have an explicit value and evidence; unknown facts have a reason; conflicting facts preserve separate evidenced claims. Cash-price fields cannot contain monthly-finance, salary or service-cost values. Money uses integer minor units and explicit currency/basis, never binary float. Description text remains source data, never system instructions. Image DTOs contain only validated supplied-listing URLs or honest missing/blocked/unverified state; Studio and Inventory own URL/evidence policy.

Hard constraints filter before soft ranking, with no implicit relaxation. Requests bound free text to 1,000 code points, clauses to 24, page size to 20 default/50 maximum, comparison to three. Cursor binds snapshot/criteria/order; mismatch is stale rather than a new unnoticed search.

Public search returns an ephemeral `PresentationProof`: ID, snapshot, ordered refs, criteria hash, issue/expiry and signature. It writes no owner/session data. Backend signs the exact canonical payload; explicit owned registration validates signature, source consistency and expiry, then saves the order under the session revision. It never trusts an arbitrary client list as the prior result order. A returned result is not proof of actual browser rendering; UI registers an owned result only through explicit user search/selection/conversation intent. Assistant invokes the same recording service after a real owned search. Prior presentations cannot be replaced by later paging/reordering.

## Revisions, durability and concurrency

- Each accepted message binds `(session_id, client_message_id)` to a canonical payload fingerprint. Exact dedupe precedes stale revision checks. Changed payload under the same ID conflicts. Provider work stays outside write transactions. Completion writes attach only to the originating turn; stale completion cannot overwrite current selection/intent.
- `MessageResult.persistence` describes only conversation-turn persistence. Fixed `actions.preferences`, `actions.shortlist` and `actions.lead` independently report not_requested/succeeded/rejected/unresolved. At most one command per domain is executed per turn; a preference patch may batch its distinct fields. Multiple shortlist/lead commands require clarification or separate turns, never extra unreported writes. Success wraps the canonical typed result and stable action ID; a saved transcript cannot imply that a preference, shortlist command or enquiry was saved. A known rejection contains a closed precondition/validation code; transient/unknown commit outcomes retain original action ID and submitted generation. Reconciliation never creates a fresh action ID; a read of current state is an observation, not proof that an earlier command did not commit. Generation change requires operator reconciliation. The same turn's exact replay reuses its original action identities/payloads. A comparison answer embeds the canonical `ComparisonResult`; it cannot replace per-car states with model prose. Viewing confirmation remains the separately typed `operation`, whose accepted lead/CSV results must be rendered independently.
- Session `criteria` retains accepted query, hard filters and soft preferences independently of prose or durable memory. A pending clarification has a stable `intent_id`, `created_revision`, closed purpose/target fields and display question. A reply supplies `clarification_reply` identity plus the ordinary expected session revision. The service must atomically match both against the current pending intent before applying its answer; mismatch is REVISION_CONFLICT/UNSUPPORTED_STATE, never reinterpretation of a newer topic. Topic changes explicitly clear/replace pending intent. These DTOs prove shape/coherence; actual stale reply and late completion behavior belongs to BE-10/BE-21 tests.
- Owned transcript GET uses `page_size` 20 default/50 maximum and an opaque signed cursor bound to owner/session, observed revision and last returned accepted revision. Return ascending accepted revision order within that fixed boundary. Each item retains stable server/client message IDs, original user text and original typed assistant result, or explicit pending/interrupted state without an invented answer. All entries are historical: embedded reviews, search results and operation observations cannot become new authority; UI reads current session/draft/operation before an action. GET never calls a provider, resubmits a turn, writes a presentation or extends retention. `current_draft_id` supports recovery without prose reconstruction.
- One active Journey per owner; New conversation retains it. Preferences save only on explicit remember/correct intent; one-time search remains session-scoped. Contacts are excluded from provider/recall context.
- Preferences use an explicit `changes` list of distinct keys, each with typed value and hard/soft strength. Null budget or empty categorical list explicitly clears that key. Each retained entry has its own source session/action, optional source message, confirmation, expiry and applicability. Updating makes must leave budget's provenance and lifetime unchanged; reads/no-op/collection-mode changes do not reconfirm entries. Owner-level revision still serializes commands. Unsupported hard preferences require clarification; free-text requirements never become fabricated structured facts.
- Shortlist commands use `(owner, client_action_id)` plus payload binding and expected aggregate revision. Every new accepted command advances revision once, including a no-op; no-op does not refresh retention. Exact replay does not reapply the command. Response includes original applied revision and authoritative **current** membership/current revision. A delayed add cannot undo a newer accepted remove.
- Shortlist GET is paginated (20 default/50 maximum) with truthful total and next cursor, including retained historical refs across snapshots. Cursor is HMAC-bound to owner, aggregate revision, stable `(added_at, namespace, snapshot_id, source_id)` order and position. Revision change returns REVISION_CONFLICT and UI restarts the read; it never silently truncates at 100 or hides an admission limit. Current/historical items contain the same exact listing ref; missing items contain no summary. Actual snapshot classification remains a service responsibility.
- Draft edits and confirmation serialize against the same authoritative revision. Material edits invalidate an unsubmitted review. An operation that may have committed must reconcile before a replacement key/review becomes actionable. Suspend/discard is a draft action, never a cancellation.
- Server-issued review binds owner, session, exact ref/resource, full UTC interval + local presentation/zone, type, rule/eligibility version, draft revision, store generation, simulation and disclosed canonical lead effect. Confirmation accepts only those review/revision/key/generation identifiers and explicit confirmation, with no replacement car/time/contact fields.
- A reviewable draft exposes a complete matching valid review. Submitted/unknown reviews expose `submitted`, never an actionable `valid` review under an unresolved draft. Review local time must equal its UTC instant with the Asia/Dubai offset; slot intervals and issue/expiry must be positive. These pure validators do not prove current capacity, opening hours, policy freshness or clocks.
- Lookup a retained terminal result before current time/capacity/expiry checks. Identical original operation replay preserves its success or rejection; changed payload conflicts. Persist terminal business rejection atomically once accepted for domain evaluation, so a later freed slot cannot turn the same rejected key into success. Transient storage failure/timeout is not terminal rejection.
- Durable rejection codes are closed to REVIEW_STALE, CAPACITY_UNAVAILABLE, ELIGIBILITY_UNAVAILABLE, RULES_UNAVAILABLE, UNSUPPORTED_STATE, SNAPSHOT_STALE and LEAD_REVISION_CONFLICT. Authentication/transport/shape failures are pre-acceptance errors; transient store/provider failures and uncertain generation observations cannot become terminal rejection. Success repeats exactly the embedded receipt's review/key/original generation.
- Owned operation status has distinct `succeeded`, `rejected`, `not_observed`, `unresolved_generation`. Missing record, cancelled fetch or response loss never proves noncommit. No retained authority yields uniform 404, still not a noncommit claim. Changed restore generation with missing proof requires operator reconciliation; no automatic old-key replay into a restored store.
- Canonical booking/lead/outbox persist together when the reviewed action includes them. CSV projection occurs after commit and has independent current/pending/failed status. Local save never means dealer delivery.

## Lifetimes and cleanup

DEMO-POLICY-1 is central policy authority. Session transcript retention is 7 days from accepted activity; preferences and shortlist 30 days from explicit update; draft inactivity 30 minutes, unsubmitted review validity 5 minutes; terminal booking/lead/outcome/retry authority 90 days; diagnostic logs/backups 7 days. Reads do not renew these periods. Unresolved authority is never auto-deleted. Expiry of session/credential/draft must not cascade-delete a retained operation or receipt. Owner/Journey skeletons persist only as required by nonexpired/unresolved dependents. At terminal expiry, old review/key authority expires together; a caller cannot reconstruct a fresh action from an expired key.

## Domain service seam

Shared repositories/models/migrations belong to Platform. Other lanes request changes. All methods receive an internal immutable `AuthorizedOwnerContext` created by verified HTTP identity or trusted adapter propagation; model/request input cannot instantiate one by choosing IDs. Services return canonical DTOs/domain outcomes, not prose success claims. Module routers are thin validation/authorization adapters. Blocking DB units run fully in one thread with one short-lived SQLAlchemy Session; no Session crosses a thread or is shared concurrently. One explicit transaction strategy owns BEGIN/commit/rollback; no network/provider/CSV work under its write lock. Detailed table invariants are in `persistence.md`.
